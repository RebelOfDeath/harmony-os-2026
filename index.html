Prologue

Meet Alex.

Alex is a software engineer. We will follow him from his first AI code completions to working with agents, and look at what it took to make each step useful and trustworthy.

Let's see what Alex is doing.

Around 2021: AI arrives in the editor.

Chapter I: The assistant in the editor

First, completion.

Alex types a signature. The model proposes the rest as grey ghost text.

Tab to accept.

Alex stays in the loop on every keystroke: accept, ignore, or keep typing.

Then, chat.

Alex asks a question in a side panel and pastes the answer back. The AI responds to the questions he asks.

Measuring it

How good are these models, really?

The field answered with benchmarks. The most reported one is HumanEval. This is its task 47.

The median of that list is 8.

The benchmark expects 15. Asked this task, ChatGPT-3.5 answered 15 too, which suggests it had seen the test before.

So we mapped the field.

247 studies, 273 AI4SE benchmarks since 2014. A third of them are about code generation. BenchScout lets you search that map by meaning.

Koohestani, de Bekker, Koç, Izadi
IEEE TSE 2025

The same flaws, again and again.

Reviewing HumanEval by hand, we kept finding wrong reference solutions, weak tests and vague descriptions. BenchFrame is our protocol for repairing a benchmark: review, modify, peer review, evaluate.

Then we re-ran the models.

On HumanEvalNext, ten code models lose 31.2 points of pass@1 on average.

Takeaway

Evaluate for your use case.

The ranking reshuffles. If we build an experience on a model we never evaluated fairly, or for our own use case, it may not behave the way we expect.

Chapter II: Opening the black box

The best assistants are black boxes.

Researchers can't pin model versions or see interaction data. Code4Me V2 is an open-source JetBrains plugin built as a research instrument.

Every signal is a module.

Adding a new telemetry signal means implementing one interface. Completions come back in about 200 ms.

Koohestani, Bateni, Ebrahimi, Etezadi, Karimi, Izadi

Chapter III: Trust

Should I accept this?

Developers need a signal for when to trust a suggestion. The model already has one: its own confidence.

Only if confidence is calibrated.

A calibrated 80% should be accepted about 80% of the time. We tested post-hoc calibration on real IDE usage at JetBrains.

One calibrator for everyone does not help.

It lowers calibration error, yet predicts acceptance no better than the average rate. Calibrating per person helps, and helps more the more we know that person.

Show it as color, in the editor.

With 3 designers and 153 professional developers, the preference was a non-numeric, color-coded signal inside the generation workflow.

Koohestani, Sergeyuk, Gros, Spiess, Titov, Devanbu, Izadi

Chapter IV: Personalization

No two developers accept the same things.

For the middle 90% of developers, acceptance rates range from 2.4% to 21.2%. The model that decides whether to show a suggestion uses one threshold for all of them.

So we tried to learn each developer.

Boosted trees with history, feedforward nets, recurrent user-state models. Several looked better on paper, but each pipeline kept different developers and rows, so the numbers are not comparable.

Then we let an agent do the research.

About 300 generations of agent-proposed pipelines, with the data and the metric frozen. None beat the best existing configuration. Revising the prompt changed the kinds of failures, and the outcome stayed the same.

The signal never reached the model.

Labelling keeps 2.16% of raw IDE events, and consecutive accepts are nearly independent. Personalization needs complete, ordered trajectories. Hold that thought.

Negative-result study, under review
Chapter V: 2025, the agents arrive

The unit of work became a task.

Alex describes the goal. The agent reads the code, writes tests, runs them, fixes what fails, and asks for review.

Alex starts delegating.

Several agents, several tasks, one reviewer. Everybody is still figuring out what this does to how we work, and what trust means now.

Researchers need to see this too.

The commercial agents are black boxes again. So we are extending Code4Me to agents, with open data collection and accessible tooling, so researchers can study how developers work with them.

In progress with Cem Gungor, Ceylin Ece, Gonenc Turanli, Mehmet Orhan Yildirim, Maliheh Izadi
Chapter VI: Assurance

Agents fail in new ways.

They loop without making progress, pick the wrong tool, or weaken a test until it passes. Each step can look fine. The problem is in the behaviour over the whole run.

From "will it fail?" to "how likely is failure?"

Agents are stochastic, so we learn a probabilistic model of the agent from its own traces while it runs, and check properties on it. When the chance of success drops, we raise an alert.

One question led to the next.

Each project picked up the question the previous one left open. Happy to go deeper in the Q&A.

Chapter VII: What comes next

Three bets, three brain teasers.

Bet 1

Personalization will be key.

Calibration improved once it knew the person. The trigger failed because history was missing. Agents leave long, complete trajectories of how each of us works.

What should your agent learn about you, and what should it never assume?
Bet 2

We will still need an IDE. An A(gentic)IDE.

People building large systems still need a place to understand, review and own code. The open questions: what it looks like, what it can do, and how we talk to it.

If most edits are no longer typed by you, what should your IDE show you first?
Bet 3

Guardrails move to the front.

Much of the industry has shipped agents faster than it has built ways to bound them. My bet: AI safety and proper guardrails become part of the product.

Who signs off when an agent merges to main?
Closing

Trust, and want to use.

Trust comes from honest evaluation, calibrated signals and guarantees. Wanting to use comes from tools that fit the person and the workflow. I think the interesting work sits where the two meet.
